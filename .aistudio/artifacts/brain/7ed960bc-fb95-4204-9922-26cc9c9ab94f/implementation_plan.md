# แผนการตรวจสอบและปรับปรุงโครงสร้างสถาปัตยกรรม (Code Audit, Security & Performance Refactoring)

รายงานการตรวจสอบจุดบกพร่อง ช่องโหว่ความปลอดภัย จุดคอขวดด้านประสิทธิภาพ และแผนการจัดระเบียบโครงสร้างโค้ดพร้อมย้ายการจัดเก็บเมนูและออเดอร์ขึ้นสู่ฐานข้อมูลกลางสำหรับ **Bluehouse Cafe QR Order**

---

## สรุปผลการตรวจสอบเบื้องต้น (Executive Audit Summary)

จากการตรวจสอบ Source Code ทุกไฟล์ในโปรเจกต์ พบประเด็นสำคัญที่ต้องได้รับการปรับปรุงดังนี้:

1. **ช่องโหว่ความปลอดภัยระดับวิกฤต (Critical Security Vulnerabilities)**:
   - **RLS Policy เปิดกว้างเกินไป (`USING (true)` ใน UPDATE/DELETE)**: ใน `supabase/schema.sql` นโยบายความปลอดภัยอนุญาตให้บุคคลทั่วไปที่ถือ public anon key สามารถลบหรือแก้ไขข้อมูลออเดอร์ของโต๊ะใดก็ได้โดยไม่ต้องผ่านการยืนยันตัวตน
   - **การคำนวณราคาฝั่ง Client (Client-Side Price Calculation)**: หน้าสั่งอาหารส่ง `price` และ `total_price` จากเบราว์เซอร์เข้าฐานข้อมูลโดยตรง ทำให้ผู้ใช้งานสามารถแก้ไขราคาสินค้าผ่าน DevTools ก่อนกดยืนยันออเดอร์ได้
   - **Mock Auth Bypass ในโค้ดสำรอง**: ใน `lib/supabase.ts` เมื่ออยู่ในโหมดไม่มี Supabase ระบบอนุญาตให้ใส่รหัสผ่านใดๆ ที่ยาวเกิน 4 ตัวอักษรเพื่อเข้าใช้งานแผงควบคุมได้

2. **ปัญหาคอขวดด้านประสิทธิภาพและความเสถียร (Performance & Reliability Bottlenecks)**:
   - **ปัญหา Polling ซ้ำซ้อนกับ Realtime**: ทั้งหน้าจอครัว (`/kitchen`) และหน้าติดตามออเดอร์ (`/my-orders`) ทำการเชื่อมต่อ WebSocket Realtime ควบคู่กับการยิง `setInterval` ดึงข้อมูลซ้ำๆ ทุก 6-8 วินาที ทำให้เกิด Network Overhead มหาศาลและสิ้นเปลืองโควต้าฐานข้อมูล
   - **State Desynchronization (เมนูแยกเครื่อง)**: เมนูอาหาร สต็อก และการปรับแต่งในปัจจุบันถูกบันทึกไว้ใน `localStorage` ของอุปกรณ์แอดมิน เมื่อลูกค้าสแกน QR บนโทรศัพท์มือถือ จะยังคงเห็นเมนูและสต็อกเดิมจากโค้ดตั้งต้น ไม่ได้รับข้อมูลที่แอดมินแก้ไขจริง

3. **โครงสร้างโค้ดและ Architecture**:
   - หน้า `/app/table/[id]/page.tsx` และ `/app/admin/menu/page.tsx` มีโค้ดรวมกันไฟล์ละ 500-700 บรรทัด มีการรวม Logic การคำนวณราคา, Modal, ตะกร้าสินค้า และการเชื่อมต่อฐานข้อมูลไว้ในไฟล์เดียว ควรแยกเป็น Custom Hooks และ Reusable Components

## User Review & Critical Decisions

> [!IMPORTANT]
> **การตัดสินใจที่ได้รับการยืนยันจากผู้ใช้**:
> - **เป้าหมายหลัก**: มุ่งเน้นการจัดระเบียบโครงสร้างโค้ดและประสิทธิภาพความเร็ว (Clean Code & High Performance)
> - **สถาปัตยกรรมข้อมูล**: ย้ายเมนูสินค้า หมวดหมู่ และออเดอร์ทั้งหมดขึ้นฐานข้อมูลกลาง (Supabase) เพื่อให้ข้อมูลซิงค์กันแบบเรียลไทม์ทุกเครื่อง

## 1. ผลการวิเคราะห์เชิงลึกตามโจทย์ 4 ข้อ

### ข้อ 1: ตรวจสอบหา Bug, Security Vulnerability และ Performance Bottleneck

| หมวดหมู่ | รายการที่ตรวจพบ | ระดับผลกระทบ | คำอธิบายและผลเสีย |
| :--- | :--- | :---: | :--- |
| **Security** | RLS Policies เปิดให้ DELETE/UPDATE สาธารณะ | **HIGH** | ใน `supabase/schema.sql` คำสั่ง `CREATE POLICY "Staff can delete orders" ... USING (true);` ทำให้ทุกคนสามารถล้างประวัติออเดอร์ทั้งหมดของร้านได้ |
| **Security** | ขาด Server-Side Price Verification | **HIGH** | ราคาถูกส่งมาจาก Payload ฝั่งลูกค้า หากมีผู้ไม่ประสงค์ดีส่งคำขอผ่าน HTTP POST แก้ไขราคาเป็น 0 บาท ระบบจะบันทึกทันที |
| **Bug / Logic** | เมนูและสต็อกหมดเก็บใน LocalStorage | **HIGH** | เมื่อแอดมินตั้งค่า "สินค้าหมด" ในเครื่องแอดมิน ลูกค้าบนมือถืออีกเครื่องยังคงสั่งสินค้านั้นได้ตามปกติเพราะ LocalStorage แยกกันคนละเครื่อง |
| **Performance** | Double Fetching (Realtime + Aggressive Polling) | **MEDIUM** | ใน `/kitchen` มีการ subscribe Postgres Changes แต่ยังตั้ง `setInterval(fetchOrders, 6000)` รันตลอดเวลา ทำให้เซิร์ฟเวอร์ทำงานหนักโดยไม่จำเป็น |
| **Performance** | ไม่มี Debounce/Throttling ในช่องค้นหา | **LOW** | การค้นหาเมนูทำการกรอง Array สดทุกครั้งที่พิมพ์อักษร แม้เมนูมี 15 รายการจะยังเร็ว แต่หากมีเมนู 100+ รายการจะเริ่มเกิดอาการหน่วง |
| **Bug** | ตะกร้าสินค้าไม่ล็อคตามโต๊ะในกรณีเปิดสลับโต๊ะ | **LOW** | เมื่อเปลี่ยน URL โต๊ะ ตะกร้าสินค้าใน Memory ไม่ได้ถูกล้าง อาจทำให้สั่งอาหารปนโต๊ะกันได้หากผู้ใช้ย้อนกลับหน้า |

### ข้อ 2: ประเมินโครงสร้าง Code / Architecture

```
โครงสร้างเดิม (Fat Page & Split State):
┌─────────────────────────┐      ┌──────────────────────────┐
│  Client Mobile Phone    │      │  Admin / Kitchen PC      │
│  - PRODUCTS (Default)   │      │  - Custom Menu (Storage) │
│  - Cart State in Page   │      │  - Polling every 6s      │
└────────────┬────────────┘      └────────────┬─────────────┘
             │                                │
             ▼                                ▼
     ┌────────────────────────────────────────────────┐
     │  Supabase Orders (Unprotected RLS & No Menu)   │

สถาปัตยกรรมเป้าหมาย (Clean Centralized Architecture):
┌─────────────────────────────────────────────────────────────┐

│            │                             │                  │
│            ▼                             ▼                  │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ Next.js API Layer (/api/orders, /api/menu, /api/auth) │  │
│  │ - Price verification & validation                     │  │
│  │ - Admin authorization verification                    │  │
│  └──────────────────────────┬────────────────────────────┘  │
└─────────────────────────────┼───────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                Supabase Central Database                    │
│  - Table: products (Central Menu & Realtime Stock Status)   │
│  - Table: categories (Dynamic Categories)                   │
│  - Table: orders (Hardened RLS Policies)                    │
│  - Supabase Realtime Channel (Event-driven updates only)    │
└─────────────────────────────────────────────────────────────┘
```

**จุดที่ต้องปรับปรุงเชิงโครงสร้าง**:
1. **แยก Logic ออกจาก View (Custom Hooks)**:
   - ดึง Logic จัดการตะกร้า (`useCart`) และการเชื่อมต่อออเดอร์ (`useOrders`) ออกจากไฟล์ `page.tsx`
2. **รวมศูนย์การดึงข้อมูลเมนู (Single Source of Truth)**:
   - สร้างตาราง `products` และ `categories` บนฐานข้อมูล พร้อม fallback cache ที่ชาญฉลาด
3. **จัดระเบียบ Folder Structure**:
   - แยก Components ย่อย เช่น `MenuCard.tsx`, `CustomizationModal.tsx`, `CartDrawer.tsx`, `OrderItemRow.tsx`

### ข้อ 3: เสนอแนะฟีเจอร์และแนวทางพัฒนาต่อยอด (Future Roadmap)

1. **ระบบพิมพ์ใบออเดอร์อัตโนมัติ (Auto Thermal Print via Bluetooth / WebUSB)**:
   - เมื่อมีออเดอร์ใหม่เด้งเข้าครัว ให้ส่งคำสั่งพิมพ์สลิป 80mm/58mm ไปยังเครื่องพิมพ์ความร้อนโดยอัตโนมัติ
2. **ระบบชำระเงิน PromptPay QR พร้อมตรวจสอบสลิปอัตโนมัติ (QR Slip Verification)**:
   - สร้าง QR PromptPay แม่มณีหรือยอดเงินเป๊ะตามออเดอร์ และให้ลูกค้าแนบสลิปเพื่อยืนยันการจ่ายเงิน
3. **ระบบจัดการคิวโต๊ะและแจ้งเตือนผ่านเสียง (Sound Chime & Audio Dispatch)**:
   - บาริสต้ากด "พร้อมเสิร์ฟ" แล้วมีเสียงกระดิ่งหรือเสียงแจ้งเตือนบนมือถือลูกค้าว่า "อาหารโต๊ะ X พร้อมเสิร์ฟแล้ว"
4. **ระบบวิเคราะห์ยอดขายและวัตถุดิบ (Inventory & Sales Insights Dashboard)**:
   - สรุปเมนูขายดีประจำวัน ช่วงเวลาที่ลูกค้าแน่นร้าน (Peak Hours) และตัดสต็อกเมล็ดกาแฟ/วัตถุดิบ

### ข้อ 4: สรุปรายการสิ่งที่ควรแก้ไขเรียงตามลำดับความสำคัญ (Action Items by Priority)

#### 🔴 ระดับวิกฤต / ความสำคัญสูง (High Priority) — ทำทันที
1. **ย้ายข้อมูลเมนูและสต็อกสินค้าขึ้นฐานข้อมูลกลาง (Supabase `products` & `categories`)**:
   - แก้ไขปัญหาการที่แอดมินปิดสต็อกแล้วลูกค้ายังสั่งได้ ให้ทั้งร้านเห็นเมนูและสถานะสินค้าหมดตรงกันทันที 100%
2. **เพิ่มการตรวจสอบราคาและข้อมูลฝั่งเซิร์ฟเวอร์ (Server-Side Price Validation)**:
   - มี API Endpoint `/api/orders` ตรวจสอบราคาสินค้า ท็อปปิ้ง และอุณหภูมิเทียบกับ Master Data ก่อนบันทึกลงฐานข้อมูล ป้องกันการดัดแปลงราคา
3. **อัปเดตและเสริมความปลอดภัย Row Level Security (RLS)**:
   - ปรับปรุง `supabase/schema.sql` ปิดกั้นไม่ให้บุคคลทั่วไปใช้สิทธิ์ลบหรือแก้ไขข้อมูลออเดอร์ของโต๊ะอื่น

#### 🟡 ระดับปานกลาง (Medium Priority) — เพิ่มความเร็วและจัดระเบียบ
4. **ยกเลิก Aggressive Polling และปรับใช้ Event-Driven Realtime ให้มีประสิทธิภาพ**:
   - ปิด `setInterval(6000)` ในหน้าครัวและหน้าติดตามออเดอร์ เปลี่ยนมาใช้ Supabase Realtime Listener อย่างเต็มรูปแบบ พร้อมระบบ Reconnection Guard
5. **แยกโมดูลหน้าสั่งอาหาร (`/table/[id]/page.tsx`)**:
   - แยกเป็น `useCart.ts`, `MenuCustomizationModal.tsx`, `CartDrawer.tsx` เพื่อลดขนาดไฟล์และทำให้โค้ดบำรุงรักษาง่าย โหลดเร็วขึ้น

#### 🟢 ระดับเสริมประสิทธิภาพ (Low Priority) — ตกแต่งและเก็บรายละเอียด
6. **เพิ่ม Cache Layer สำหรับเมนูหน้าร้าน (SWR หรือ React Query Pattern)**:
   - ช่วยให้เมื่อลูกค้าเปิดเมนู โหลดขึ้นมาได้ทันทีใน 0.1 วินาที แม้สัญญาณอินเทอร์เน็ตบนมือถือจะช้า
7. **เพิ่ม Debounce ในการค้นหาเมนู**:
   - ป้องกัน Re-render ถี่เกินไปเมื่อพิมพ์คำค้นหา

## 2. แผนการดำเนินงานทางเทคนิค (Technical Execution Plan)

### เฟสที่ 1: การอัปเกรดฐานข้อมูลและความปลอดภัย
- ปรับปรุง `supabase/schema.sql`:
  - สร้างตาราง `public.categories` และ `public.products`
  - อัปเดต RLS Policy ของ `public.orders` ให้ปลอดภัยยิ่งขึ้น
  - จัดเตรียม SQL Script ให้รันผ่าน SQL Editor ได้ทันที

### เฟสที่ 2: สร้าง Server API สำหรับจัดการเมนูและตรวจสอบออเดอร์
- สร้าง `/app/api/orders/route.ts`: ตรวจสอบความถูกต้องของรายการอาหารและคำนวณราคาสุทธิบน Server
- อัปเดต `lib/supabase.ts` และ `lib/config.ts`: ให้รองรับการดึงข้อมูลเมนูทั้งแบบ Local Fallback และแบบ Live Database

### เฟสที่ 3: ปรับปรุงประสิทธิภาพหน้าจอครัวและหน้าสั่งอาหาร
- ลบ Aggressive Polling ออก ปรับปรุงการ Sync ผ่าน Realtime Channel ให้ตอบสนองทันทีแบบไร้รอยต่อ
- จัดระเบียบ Component ฝั่งลูกค้าและแอดมินให้มีความสะอาด เป็นระเบียบ และทำงานได้รวดเร็วที่สุด
